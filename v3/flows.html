Airframe · system flows

From live air to "what, where, how to fix" and learning what's new

Part 1 finds what is wrong and where, in real time. Part 2 is an AI agent that proposes the fix. Part 3 keeps a catalog of every known error and uses a second AI agent to turn unknown events into new catalog entries. Each part has a high-level and a deep-level flow.

OverviewReal timePart 1Part 2Part 3

Overview The whole system

Three parts share one error catalog. Known problems flow left to right to a fix; unknown ones flow down into the learning loop and come back as new catalog entries.

Part 1 · What & where

Input: live frames from every sensor
Does: decode, mask, rebuild device stories, match the catalog, count each problem once
Output: incidents with location, severity, confidence; live dashboard

Part 2 · How to fix (AI agent)

Input: one incident + its catalog entry + evidence + site context
Does: investigates with read-only tools, ranks causes, picks the confirming check
Output: fix proposal: cause, confirm step, fix, owner, risk, rollback, success test
Human: approves → ticket; Part 1 checks the success test live

Part 3 · Learn new problems (AI agent)

Input: events no catalog entry matched (OTHER)
Does: clusters, investigates, drafts a new entry + rule + fix, backtests
Output: catalog v+1 after human review; detectors hot-reload

Part 1 Find WHAT is wrong and WHERE

Runs continuously on the stream. Every detector is a catalog entry, so "what" always has a name, a plain-language meaning and a standard fix.

Deep level

1 · Decode
1.1Frame row

sensor, time, rate, channel, signal, type, flags, addresses, sequence, codes, EAP, EAPOL message no.

1.2Mask first

HMAC-SHA256 of MACs with a site secret; SSIDs become NET-C/NET-T; EAP identities dropped.

1.3Role + direction

Beacon sender = AP; from-DS/to-DS decide who transmitted; ACKs have no sender.

↓
2 · Track
2.1Beacon tracker

Per BSSID: interval, loss, rate, security type, networks per AP.

DISC-01DISC-05RF-03
2.2Sliding counters

1 s / 60 s per AP, channel and client: probes, retries, airtime.

DISC-03RF-01
2.3Episode state machine

Per device + AP: auth → assoc → EAP → M1..M4 → connected → left, with event-time timers.

EAP-01SESS-01/02
↓
3 · Judge
3.1Proof rules

AP side first: M3 proves a valid M2; status 0 proves the request; Block-Ack setup proves association.

3.2Could a sensor hear it?

No → "not observed", info only (KEY-06). Yes → real "missing" evidence.

3.3Catalog match?

Yes → detection with entry id. No → OTHER-CODE / SEQ / STAT to Part 3.

↓
4 · Count once
4.1Merge

Same device + entry within 5 s across sensors = one incident with "seen by".

4.2Root grouping

Same entry on ≥3 APs or ≥2 channels in 2 min → one root, devices as children.

4.3Causal links + control

Loops, fast rejects, probe storm attach to the root. Healthy SSID on same radios = control.

↓
5 · Locate + publish
5.1Score

Severity (devices × duration × network); confidence lowered by blind spots and data-quality flags.

5.2Where

APs, channels, sensors, time window, blast radius (device / AP / channel / site).

5.3Lifecycle + push

open → updating → resolved (quiet 2 cycles) → closed; pushed to dashboard and Part 2.

Part 2 AI agent proposes HOW TO FIX

A Claude-based agent with read-only tools. It never touches access points, controllers or RADIUS; people apply fixes. Part 1 then checks, live, whether the fix worked.

→

→
Ticket → verifyPart 1 watches the success test
↺ Not resolved after the window → back to the agent with the new evidence. Resolved → outcome stored in the knowledge base for next time.

Deep level

1 · Trigger + context
1.1Trigger

New or escalated incident of severity high or above, or an engineer clicks "Explain & fix".

1.2Context pack (masked)

Incident JSON, evidence refs, catalog causes/checks/fixes, control comparison, timers, similar past incidents, site inventory, change calendar.

↓
2 · Agent loop
2.1Restate facts

Only what evidence shows.

2.2Hypotheses

From catalog causes and history, ranked.

2.3Test with tools

Evidence for and against each hypothesis.

get_timelinequery_framescompare_controlcatalog_lookup
2.4Deciding check

The one outside check that separates the top two causes, e.g. "are requests reaching RADIUS?"

2.5Fix plan

Steps, owner team, risk, rollback.

2.6Success test

Something Part 1 can measure, e.g. reason-23 count = 0 and EAP success > 95% for 10 min.

↓
3 · Guardrails
3.1Read-only

No write tools exist; no transmission, no config change.

3.2Cite + validate

Every claim cites evidence ids; every code checked against the IEEE tables; output schema-validated.

3.3Confidence ≥ 0.6?

No → "needs human" plus the missing fact to collect. Yes → proposal.

↓
4 · Decide + close
4.1fix_proposal.json

Shown next to the incident on the dashboard.

4.2Engineer decision

Approve → ticket to AAA / network / device team. Edit → back to loop. Reject → reason stored.

4.3Verify live

Part 1 checks the success test; resolves the incident or re-opens it for the agent.

Part 3 Error catalog + learning unknown errors

The catalog (79 entries, 13 categories) maps every IEEE reason and status code, except the reserved ones, to a named problem. Anything that matches nothing is stored as OTHER and investigated by a discovery agent, which proposes new entries for human approval.

High level

Every eventframe, sequence, metric
→
In catalog?yes → Part 1 incident → Part 2
→
OTHER storeno match, kept with context
→
Discovery agentcluster, investigate, name it
→
Draft + backtestentry, rule, fix; run on stored data
→
Human reviewapprove → catalog v+1
↺ New version hot-reloads detectors, re-classifies stored OTHER events, and gives Part 2 new causes and fixes.

Deep level

1 · Capture unknowns
1.1OTHER-CODE

Reason/status/EAP code not mapped (reserved or vendor-specific values).

1.2OTHER-SEQ

Device story hit a transition the state machine does not define.

1.3OTHER-STAT

A metric jumped (z-score > 4) and no detector explains it.

1.4Record

Masked ids, frame fields, ±10 s timeline, co-occurring incidents, metrics.

↓
2 · Discover
2.1When to run

Cluster ≥ 20 events, a high-severity hint, or hourly.

2.2Cluster

By code, transition, metric, sender role, device class.

2.3Investigate

Timelines, IEEE code text, related entries, change log (read-only).

2.4Variant or new?

Extend an existing entry, or draft a new one in the catalog schema.

↓
3 · Validate
3.1Safe rule DSL

JSON: match fields + window + group-by + threshold. No free-form code from the model.

3.2Automatic checks

Schema, unique id, every code exists in the IEEE tables.

3.3Backtest

Fires on the cluster, stays quiet on healthy periods (false-positive estimate).

↓
4 · Adopt
4.1Human review

Approve, edit, or reject (reject labels the cluster "benign" so it stops recurring).

4.2Merge

Version bump + changelog.

4.3Hot reload

Part 1 detectors reload; stored OTHER events re-classified; Part 2 learns the new fix.
