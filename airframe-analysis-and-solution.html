Reading the air on a plant floor

Three of our four sensors show Wi‑Fi handshakes that look broken. None of them are broken.

For each of those joins, the sensor caught only the access point’s side. The client’s half never reached it, but the access point’s replies prove it happened. That single lesson shapes the whole solution: judge a client by all the evidence from all sensors, never by one sensor’s gaps.

1The problem in plain words

A Tesla plant runs a lot of Wi‑Fi: handhelds, torque tools, label printers, AGVs, laptops, sensors. When a device cannot connect, or keeps dropping off, production feels it long before anyone opens a ticket.

To see what is happening, small listening boxes called sensors sit on the floor and record the Wi‑Fi traffic they can hear, the way a microphone records a room. Each sensor saves what it hears into one capture file (a pcap). We get several of these files from the same area.

Two things make this hard:

  • We only see envelopes, not letters. The captures keep the frame headers (who sent what kind of message to whom), but not the content. We cannot see IP traffic, DHCP, DNS or applications.
  • Several microphones hear the same room. The same device, or the same failure, can appear in two or three files. Each file may hold only part of the story. Three recordings of one problem are one problem.

The job: turn these files into a clear list of real problems (which clients fail, where the air is congested, which events are the same event seen twice) and show it on a dashboard.

2Four ideas you need first

Channel

Wi‑Fi is split into numbered frequency lanes called channels, much like radio stations. Devices on one channel cannot hear devices on another, even when they stand side by side. Everything on the same channel in the same space shares that lane, and only one device can talk at a time. Too many talkers on one lane is congestion. A sensor records one channel at a time.

Area

An area is a physical zone of the floor. Each sensor has a rough circle around it inside which it can hear transmissions. Whoever is inside that circle and on the sensor’s channel is what the sensor records.

Who produces the data: access points or sensors?

The sensors. Access points (APs) and client devices just do their normal work and have no idea they are being recorded. The sensors listen passively, never transmit, and write what they hear to a pcap. One sensor, one file, one point of view.

Overlapping

Sensors close to each other have overlapping circles, so they can record the same event. But overlap in space is not overlap in data: if two nearby sensors listen on different channels, they record completely different conversations.

The source column says STA-05, a client. But the F flag (“From DS”, from the distribution system) means an access point put this frame on the air. The AP was relaying the client’s message back out to the other devices. The client did not transmit this frame.

The flag letters

A normal join, in order

  1. Authentication: “may I talk to you?” / “yes”. On these networks it is the simple open exchange; the real security comes later.
  2. Association: “I want to join this network on you.” The AP answers with a status code. Zero means accepted; anything else is a rejection.
  3. 802.1X / EAP (enterprise networks only): the device proves who it is to a RADIUS server. Skipped on pre-shared-key networks.
  4. 4-way handshake (EAPOL messages M1 to M4): AP and client agree on encryption keys without sending the password. M1 and M3 come from the AP, M2 and M4 from the client.
  5. Encrypted data starts flowing. We see only that it flows, never what it says.

Around all this, every AP sends a beacon about ten times a second (every 102.4 ms, which is what BI=100 means: 100 time units of 1.024 ms). Beacons are the AP’s heartbeat. Unicast frames are confirmed by a short ACK; broadcast and multicast frames are never ACKed.

4How the analysis was done

The frames were parsed with code rather than read by eye, so every number in this document can be reproduced.

  1. Sort by time. The pasted listings were displayed out of frame order (for example frame 15 before 14). In the files, frame number and time agree, so the pipeline always sorts by timestamp.
  2. Decide who transmitted each frame. Use the To DS / From DS flags and the frame type, not the “source” column. ACK frames carry no sender address at all; attribute them to the device that received the frame before.
  3. Rebuild each client’s ladder: authentication, association, EAP, M1 to M4, data.
  4. Apply inference rules. Some frames prove others happened even when those others were not heard (table in section 5).
  5. Compare sensors: which APs and clients each sensor hears, and whether any appear in more than one file.
  6. Check timing and beacons: join durations, beacon intervals, missed beacons.
  7. Sanity-check the data itself: does the capture behave like real radio? (It mostly does not; see finding F6.)

5What the captures show

F1. All five joins in the excerpts succeeded.STA-05, STA-06, STA-07, STA-08 and STA-09 each join the tools network and pass encrypted data within 58 to 82 ms. There are no rejections, deauthentications, retries or EAP exchanges in any excerpt.
F2. Sensors 1 and 8 heard nothing a client transmitted.Every one of their 63 frames came from an access point: beacons, the AP’s half of each join, and the AP relaying client data. Sensor 7 heard one client’s uplink (STA-03) but not the joining client’s (STA-08), so this depends on where each client stands, not on the sensor.

F3. Each sensor hears a different set of access points.No AP network is heard by two sensors. That strongly suggests the sensors listen on different channels, exactly as the challenge brief warns. Cross-sensor correlation will have to work through shared clients and APs where they exist, not through identical frames.
F4. The tools network uses a pre-shared key; the corporate network is unverified.On SSID-T the 4-way handshake starts straight after association with no EAP exchange, and the 47-byte authentication frames match the simple open exchange, not WPA3’s SAE. So failures on SSID-T will look like key mismatches, not EAP failures. No SSID-C joins appear in the excerpts; its security type must be read from the RSN element in its beacons.
F5. Beacon health is fine, with two isolated misses.Beacons arrive every 102.6 ms on average (expected 102.4). Sensor 1 missed one beacon from AP-01/T and sensor 3 one from AP-07/T. Two networks were never heard at all (AP-14/T by sensor 1, AP-08/C by sensor 7), which may be range or configuration. Far too little data to call a problem.
F6. These captures look emulated, not recorded over real air.Beacons from different APs on the same channel arrive 1 µs apart. On real air a beacon of this size occupies roughly 0.35 ms even at 6 Mb/s, so two cannot sit 1 µs apart. Every beacon has sequence number 0, and every AP uses the same counters (127, 128, 130) for every join. That is fine for a hackathon, with one consequence: protocol-sequence logic transfers to production, but airtime and congestion maths from timestamps will not be physically meaningful on this dataset.
F7. The excerpts are too short to judge the site.Less than half a second per sensor, 145 frames in total. The failures the challenge describes (loops, storms, stalled handshakes) are almost certainly elsewhere in the full files. The value of this excerpt is that it exposes the trap: a naive tool would have reported four failed handshakes here.

Beacon overhead, a quick plant rule. Sensor 1 hears 9 networks on its channel. At 6 Mb/s their beacons take roughly 3% of airtime; if the lowest allowed data rate is 1 Mb/s (common on 2.4 GHz), the same beacons take nearly 20%, before a single useful frame is sent. Every extra SSID multiplies this. Check the rate field in the capture before blaming clients for congestion.

8The solution: prototype design

A laptop pipeline that reads all pcaps, rebuilds every client’s story from every sensor, and reports one finding per real event.

1. Extract

Use tshark to pull only the header fields we need into a table (CSV, then Parquet). Field names vary slightly between Wireshark versions; check them with tshark -G fields | grep -E "msgnr|status_code|reason_code".

tshark -r sensor01.pcapng -T fields -E header=y -E separator=/t -E occurrence=f \
  -e frame.time_epoch -e frame.len \
  -e radiotap.channel.freq -e radiotap.dbm_antsignal -e radiotap.datarate \
  -e wlan.fc.type_subtype -e wlan.fc.ds -e wlan.fc.retry -e wlan.fc.protected \
  -e wlan.ta -e wlan.ra -e wlan.sa -e wlan.da -e wlan.bssid -e wlan.seq \
  -e wlan.fixed.status_code -e wlan.fixed.reason_code -e wlan.fixed.timestamp \
  -e wlan.ssid -e wlan.ds.current_channel \
  -e wlan_rsna_eapol.keydes.msgnr -e eapol.keydes.replay_counter \
  -e eap.code -e eap.type  > sensor01.tsv

If the radiotap header lacks channel or signal (the 27-byte ACKs suggest a small, roughly 13-byte radiotap header), read the channel from the beacon’s DS Parameter element (wlan.ds.current_channel).

2. Normalise

For every frame decide the true transmitter and direction (To DS, From DS, management, control), convert to absolute time, and replace every MAC with a keyed hash (HMAC-SHA256, secret salt kept out of the repository, first 8 hex characters). SSIDs become labels; EAP identities are never shown. Keep the vendor prefix as a device-type hint.

3. Align clocks

Each pcap starts at its own zero. Every beacon carries the AP’s own timestamp (TSF). The same beacon, identified by BSSID and TSF, heard by two sensors marks the same instant, which gives the clock offset between those sensors. Fallback anchor: the same unicast management frame (transmitter, sequence number, type) in both files.

4. De-duplicate

After alignment, frames with the same transmitter, receiver, type, sequence number, retry flag and EAPOL message number within ±5 ms are one frame. Keep one row with a list of observations (sensor, signal strength). The sensor with the strongest signal becomes primary.

5. Build episodes

Per client: a new episode starts at authentication, association or reassociation, and ends when data flows, a deauth arrives, or 5 s pass. Each stage is marked seen (by which sensor), inferred (by which rule from section 5), or missing. “Missing” is only allowed if a sensor that normally hears that transmitter was listening at that moment; otherwise it is not observed. This one rule removes most false alarms.

6. Detect

Run the rules from section 7 on the episodes and on per-transmitter counters (retry share, beacon loss, networks per channel, probe rate, signal trend).

7. Incidents

One incident per client per problem per time window, not per sensor and not per frame. A deauth loop of eleven cycles is one incident with a count of eleven. Each incident lists the sensors that contributed evidence, so the dashboard can say “seen by S7 and S8, counted once”.

8. Dashboard

Five views: floor overview (KPIs and per-sensor health), incident list, client drill-down with the merged ladder colour-coded by sensor, channel health, and sensor health. Streamlit with Plotly is the quickest path on a laptop; Grafana on SQLite or DuckDB works too.

10Optional: design for thousands of sensors

Design only, as the brief asks. The core idea: parse at the edge, ship small events, correlate per site in a stream, and keep raw captures only when something is worth a second look.

Volume, backpressure and what to keep

Illustrative sizing, to be replaced with measured rates: 5,000 sensors each hearing about 20 networks produce about 200 beacons per second each, roughly a million beacons per second fleet-wide, most of them telling us the same thing. So the sensor summarises beacons into one record per network every 10 s (count, missed, signal min/mean/max, channel, a hash of the elements to spot configuration changes) and data-frame headers into per-transmitter counters per second (frames, retries, bytes, rate). Authentication, association, EAP, EAPOL and deauth frames are rare and precious, so they are sent verbatim. That removes well over 90% of the volume.

Sensors buffer about an hour locally in three priority lanes. Under pressure they drop raw snippets first, then thin out summaries, and never drop join, security or deauth events.

Overlap without storing everything twice

The correlator partitions by site and floor, so every sensor that could hear the same event lands on the same worker. It emits one canonical event with a list of observations (sensor, signal, local time) instead of one copy per sensor.

Sensor lifecycle

Sensors enrol with a device certificate and are registered with site, floor, position and assigned channel. A heartbeat every 30 s reports frames per second, beacons heard, clock offset and backlog. A healthy sensor always hears beacons, so “no beacons for two minutes” means the sensor is deaf, unplugged or on the wrong channel. Firmware goes out in rings (a few canaries, then one site, then the fleet) and rolls back on heartbeat regressions. Retiring a sensor revokes its certificate; its ID is never reused.

Trade-offs we chose

ChoiceGainCost, and how we soften it

The biggest limitation is simple: 145 frames across four sensors. No deauthentications, probes, retries or EAP appear in them. Everything in sections 7 to 10 is designed for what the full captures are likely to contain, and should be validated against them first.

The most useful habit this review produced: before calling anything missing, ask who transmitted it and whether any sensor was in a position to hear it.

AGlossary and code skeleton

AP (access point)
The Wi‑Fi “base station” that devices connect to.
Client / STA
Any device that connects to an AP: tool, handheld, AGV, laptop.
BSSID
The address of one network on one AP. One AP can run several (here: C and T).
SSID
The network name users see.
Beacon
An AP’s “I am here” broadcast, about ten per second per network.
ACK
A tiny “got it” reply to a unicast frame.
Retry flag
Marks a repeated attempt; the main sign of loss or congestion.
Sequence number (SN)
A counter per transmitter; repeats mean retries, jumps can mean unheard frames.
To DS / From DS
Direction bits: client-to-AP or AP-to-client.
EAPOL M1 to M4
The 4-way handshake that creates encryption keys.
802.1X / EAP
Enterprise login where a device proves its identity to a RADIUS server.
PSK
Pre-shared key: one passphrase shared by all devices on the network.
Deauthentication
“You are disconnected”, with a reason code.
Roam
A client moving from one AP to another. Normal.
TSF
The AP’s internal clock, stamped into every beacon; used to align sensors.
Radiotap
Extra header added by the sensor: channel, signal strength, data rate.
DFS
Rule that makes 5 GHz APs leave a channel when radar is detected.

Python skeleton for stages 2 and 5

A starting point, not finished code. Adjust field names to your tshark version.

import hmac, hashlib, collections

SALT = b"load-from-env-never-commit"
def mask(mac):
    return mac and "m_" + hmac.new(SALT, mac.encode(), hashlib.sha256).hexdigest()[:8]

MGMT = {0x00: "assoc_req", 0x01: "assoc_resp", 0x02: "reassoc_req", 0x03: "reassoc_resp",
        0x04: "probe_req", 0x08: "beacon", 0x0a: "disassoc", 0x0b: "auth",
        0x0c: "deauth", 0x0d: "action", 0x1d: "ack"}

def normalise(r):
    st = int(r["wlan.fc.type_subtype"], 0)
    ds = int(r["wlan.fc.ds"] or "0", 0)           # 1 = To DS, 2 = From DS
    kind = MGMT.get(st, "data" if st in (0x20, 0x28) else hex(st))
    msg = r.get("wlan_rsna_eapol.keydes.msgnr")
    if msg: kind = f"M{msg}"
    tx = r["wlan.ta"] or None                      # ACKs have no transmitter
    return dict(t=float(r["frame.time_epoch"]), sensor=r["sensor"], kind=kind,
                tx=mask(tx), rx=mask(r["wlan.ra"]), sa=mask(r["wlan.sa"]),
                bssid=mask(r["wlan.bssid"]), ds=ds,
                retry=r["wlan.fc.retry"] in ("1", "True"),
                status=r["wlan.fixed.status_code"], reason=r["wlan.fixed.reason_code"])

def client_of(f):
    if f["ds"] == 2: return f["sa"]                # AP relaying: client is the source
    if f["tx"] == f["bssid"]: return f["rx"]       # AP -> client
    return f["tx"]                                 # client -> AP

def verdict(ev):                                   # ev: set of kinds seen for one episode
    if "relayed_data" in ev or "client_data_acked" in ev: return "joined"
    if "M3" in ev: return "4way_stall"
    if "M1" in ev: return "key_mismatch_or_m2_lost"
    if "assoc_resp_ok" in ev: return "eap_or_pre_4way_failure"
    return "assoc_rejected_or_abandoned"
